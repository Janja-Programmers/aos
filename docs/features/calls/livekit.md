# Calls LiveKit security

Calls uses the repository's shared LiveKit service but owns a Calls-specific security boundary.

- Room names are generated by the server on `AOS Call` creation and are immutable.
- RTC identity is the participant's opaque public `ACC-*` ID, never User/email.
- Clients cannot request an identity, room, role, or grant set.
- Calls grants remain the minimum required for two-way calling: room join, media publish, subscribe, and data publish. No room-admin grant is issued.
- Calls token lifetime is bounded to 1–5 minutes even if a longer legacy setting exists.
- The receiver receives an RTC token on accept, or through reconnect only after the call is `ongoing`.
- Active account state and bidirectional Social block policy are rechecked before token issuance.
- LiveKit signing/configuration failures are returned as `CALL_DEPENDENCY_UNAVAILABLE`; JWTs and provider secrets are never logged.

## Room cleanup and reconciliation

Terminal transitions set `room_cleanup_pending`. Deletion is queued after transaction commit and a bounded five-minute scheduler retries pending cleanup. Provider failure does not roll back the authoritative call transition.

For `ongoing` calls older than five minutes, reconciliation checks account/social policy and then observes the LiveKit room without holding application DB locks. A missing room must be observed twice at least five minutes apart before the existing `failed` state is used. An authorized reconnect clears the missing-room marker, preventing a scheduler/reconnect race.

## Webhooks

The current repository has a signed/deduplicated global LiveKit webhook path for the **Live** feature. It does not model Calls participant/lifecycle webhooks. Calls therefore does not invent a webhook event ledger or participant states. Calls recovery relies on authoritative APIs, timeout workers, durable room cleanup, and conservative room reconciliation.
